# A2A 协议

Clowder AI 在一个共享线程中运行着许多 Agent。Agent 间（A2A）协议就是**单条消息的生命周期**——从它出现的那一刻起，穿过共享的时间线，直到某个 Agent 产出结果，以及一旦出错用户会看到什么。

它不是一条路由流水线，而是一个投递内核，回答一个精确的问题：一个输入何时仅存在于队列中，它何时进入共享时间线，队首何时必须被调度，它如何被交给某个 Agent，回复如何就地终结，以及在失败或重启之后用户会看到什么？

## 系统追踪的三样东西

投递内核恰好构建在三个对象之上。其他所有东西——正文暴露、等待/重试状态、结构化责任——都归属于各自的所有者，只被引用，绝不被复制。

| 对象 | 是否持久化 | 它是什么 |
|---|---|---|
| **队列条目（Queue Entry）** | 是 | 一个有序的待处理输入，加上其可恢复的来源身份和入队时的目标*意图*。**只要它还在队列中，正常的派发就尚未开始。** |
| **聊天历史消息（Chat History Message）** | 是 | 已进入聊天面板的一个输入、Agent 消息或回复气泡。它有一个固定的排序键；真正被投递的公开消息携带因果性的 `dispatchRefs`，指向其确切的目标与结果。 |
| **活动运行（Active Run）** | 否（在内存中） | 内核的一条记录，表明它为某一个 Agent 准入了特定的输入，以及该 Agent 的那一个回复气泡。它是执行图景中的*一个输入*——而非执行的全部真相。 |

关键的区分在于：**一个公开输入仅存在于队列中**——对聊天面板和其他 Agent 的上下文都不可见——直到单个准入步骤将它物化进历史。

## 一条消息的旅程

一个正常的输入会经历七个步骤：

1. **来源构造消息。** 用户、连接器、系统、Agent 或既有的协议所有者已经决定了内容、目的和目标。内核不会去重新猜测意图。
2. **它持久化进入队列。** 入口点将来源信封包装为一个队列条目。公开输入、Agent 唤醒和私有输入都进入*同一个*持久化优先级队列，然后触发一次排空（drain）。
3. **严格选取队首。** 每线程的排空只查看比较器计算出的那一个队首。如果目标繁忙，它就等待；它绝不会去扫描"更优"的候选，也绝不会跳过队首。
4. **准入——唯一的切换点。** 一个事务将条目提升（或复用）为一条历史消息，把每个目标的引用翻转为 `dispatched`，并为每个目标创建一个固定的 `processing` 回复气泡。**只有在该事务提交之后**，内存中的活动运行才会被创建，Agent 才会被调用。
5. **同一个气泡进行流式输出。** 输出只更新准入所创建的那个气泡。一个成员内部的会话滚转、上下文压缩或续写都停留在 Agent 客户端内部，不会创建新的内核对象。
6. **就地产生唯一的终态。** completed、failed 或 canceled 都会就地终结*同一个*气泡；在一个持久化事务中，每个结构化所有者提交自己的处置，并且只创建该结果所允许的后续动作。
7. **释放，然后继续。** 终态提交之后，那个确切的活动运行被释放，排空再次运行——这样下一个排队项就绝不会无声地干等着。

## 排序与优先级

只有一个持久化队列，配一个稳定的比较器：手动放置的行优先（按位置），然后 `urgent` 先于 `normal`，最后按入队时间遵循 FIFO。**不存在第三种由消息类型、来源或类别派生出的隐藏优先级。** 通过拖拽重新排序会针对预期的队列修订版本原子地提交整个可见顺序——因此只有显式的手动操作才会覆盖默认的优先级与 FIFO。

## 工作如何被取走——以及为何不会卡住

排空是**事件驱动的——不是定时器，也不是优先级调度器。** 它只在某件事真正改变了队首可执行内容之后才运行：一次入队、一次移除或重排、一个活动运行完成、一个外部所有者就某个尚未准入的候选提交了一个事实，或者启动时发现了一个非空队列。一个脏位（dirty-bit）保证了在排空进行途中到达的事件，会在排空所有者被释放之前强制再进行一轮。

其结果是一个结构性不变量，而非一个看门狗：**系统不可能稳定地停留在"队列非空、队首可执行、没有活动运行、且没有排空"的状态。** 任何东西都不会无声地堆积起来。

## 回退——当没有给出目标时

回退**仅适用于队首的公开消息，且仅当线程空闲时**（没有活动运行）。如果最近一个**已完成（completed）**回复气泡的成员可用，它就路由给该成员；否则路由给服务器的默认成员；再否则就呈现一个可见的投递失败。最近气泡处于 processing、failed 或 canceled 状态的成员不作为候选。

**显式目标以及私有或结构化的工作绝不回退。** 一个失败的确切目标会产生一个带类型的失败和诊断信息——绝不会无声地重新指派给其他人。

## 一个回合如何结束

一个活动的 Agent 恰好产出三种结果之一——**completed、failed 或 canceled。** 第四种，**interrupted**，是在某个运行已被准入但其活动客户端已消失时，由启动恢复合成出来的；它会收敛到失败路径上。每种结果都会就地终结*同一个*回复气泡——部分流式输出会连同一个状态页脚一起被保留，绝不会被替换成一个通用的错误。一个已提交的终态即为最终态：同一代的重放会返回那个已经提交的结果，而不是产生第二个答案。

## Agent 之间的交接

有两种不同的东西都被称作"交接"，而只有一种对协议可见：

- **成员内部续写**——一个 Agent 压缩上下文或滚转其会话以完成同一次调用。这对生命周期不可见：仍是同一次调用，仍是同一个回复气泡。
- **协议可见的 A2A 交接**——一个携带有效目标的已完成回复（或一次显式的 `post_message`）。它创建一个引用*同一条*回复消息的唤醒——它**不会**被复制成第二条消息——然后下一跳开始。

每一跳都**独立地终结，并且只关闭它自己的 `input → target` 步骤。** 如果 Agent B 在回答 A 的过程中提及了 D，那*并不会*重新打开 A→B，也不会让 A 递归地去等待 D。在**失败**时，在处置掉那次确切的调用之后，托管权只会返回给**来源所有者所指名的那个确切前驱**——绝不会从消息的作者字段推断出来。用户、连接器以及计划任务或公开输入没有这样的所有者绑定，永远不参与前驱返回。

## 每个参与者看到什么

用户和 Agent 读到的是**相同的顺序**，由历史排序键串联。如果 A 先开始而 B 先完成，最终顺序仍然是*A 的气泡 → B 的气泡*，而不是完成顺序。一个 `processing` 气泡是一道 Agent 的读取游标不可跨越的**排序屏障**，因此后完成的工作绝不会插到前面去。

"Processing"意味着服务器端的执行正在进行。它**并不**意味着 Agent 已经看到或读过内容：正文暴露和"已处理"是两个独立的事实，各有其所有者。

## 用户控制

四种显式操作作用于特定的条目或运行。它们*不是*对正常调度的补救手段，也绝不会暂停或重排队列：

- **追加（Append）**——将你的输入添加到目标*现有*的运行中；不创建新的运行。
- **引导（Steer）**——取消该目标仍在进行的运行，然后准入一个全新的运行。
- **取消排队项（Cancel queued）**——删除一个尚未派发的条目；不影响任何运行。
- **停止 Agent（Stop agent）**——对确切的活动 Agent 运行进行快照并取消它们；正常的 `canceled` 回调会关闭气泡。（受管命令和作业不在此快照中。）

## 线程独立性

每个线程都有它自己的事件驱动排空和它自己的队首。一个线程中的工作绝不会串入另一个线程的调度；线程之间任何共享的东西都是一次显式的、有记录的交叉张贴（cross-post）。

## 设计原则

整个模型建立在五条规则之上：

1. **每个事实只有一个所有者。** 每个事实——排队的输入、已准入的调用、正文暴露、公开结果、结构化责任——都恰好有一个所有者。其他所有人都引用它；没有人复制它并重新裁定它。
2. **在唯一的切换点上改变。** 顺序、副作用以及下一个由谁行动，只在单个持久化准入事务提交时才改变。
3. **不要从一个事实推断另一个事实。** 已派发不等于已看到；已落定不等于已处理；入队目标只是意图，会在派发时重新校验。
4. **每个运行只有一个终态。** 每个已准入的运行恰好有一个就地的结果；一个已提交的裁决无法被撤销或复制。
5. **投影是可重建的；失败关闭（fail-closed）。** 头像、"processing"和引用全都派生自权威事实。当证据缺失或含糊时，省略动态断言并显示一个诊断信息——绝不伪造"已看到""正在处理"或"已完成"。
