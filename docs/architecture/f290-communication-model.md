# F290 通讯模型与执行上下文

本页把 09-30 共创结论写成实施约束，供 [F290 spec](../features/F290-ai-native-collective.md) 与
可用版本计划 (internal) 共同引用。它是通讯细节的阅读入口；
Feature 继续拥有范围与验收状态，原计划继续拥有交付顺序。下文的目标行为不代表已经实现，
不新增 runtime 权限，不解除已有 Alpha/UAT 暂停，也不把 Pro 研究建议整体视为获准设计。

## 1. 对象与真相归属

| 对象 | 保存什么 / 谁负责 | 不能拿它冒充什么 |
|---|---|---|
| 家内猫身份 | 既有 catId、配置、模型绑定与主人允许的身份/家规，由现有 Cat runtime 管理 | 为 Collective 另建一套“公共猫人格” |
| 公共参与身份 | 现有 Service/connection/cat provenance、所属 Café、参与范围和 accountable human | 猫的昵称、当前模型或一条 LLM session |
| Channel 接收端 | Host 内每 Café×Channel 的逻辑收件关系；同时校验 Service/Collective 范围；持久游标、关注、上下文胶囊、多猫关联 | 每只猫一个端点、一个永远运行的模型、所有工作共用的固定地址 |
| Channel / Topic | Service 的公共对话、消息及来源关系 | 家内私人 Thread 或主人授权 |
| Work | Service 的公共事项、current assignment、结果与责任历史 | 每条闲聊、一次工具调用或内容版本 |
| Task / 工作 Thread | Host 经有效准入建立的家内任务与执行现场 | 第二份公共 Work 真相或可随意对外读取的历史 |
| Artifact / version | 内容 owner 的对象、正文与版本；F290 消费来源、权限、lineage 和结果目标 | Work 的 resultRevision 或工作验收 |
| Memory / 索引 | 有来源、按权限过滤的查找与理解材料 | 当前消息、工作状态、授权或统计的唯一真相 |

**基数例子**：You 的 Café 若获准参与 10 个 Collective 的各 10 个 Channel，就有 100 份逻辑
频道接收关系；每个频道有多只猫，也不再乘猫数。加入 Collective 不自动等于获准参与其中所有频道。
这不要求 100 个常驻 LLM、100 份全量 prompt 或 100 只猫同时读消息。接收 Thread 提前建立还是
首次需要时物化仍是实现选择，不能把“100 个逻辑端点”写成已定的物理创建策略。
消息、接收关系、用户偏好和工作责任默认持久化（TTL=0）；临时调用与可过期 presence 另算。

## 2. 出门的是家里同一只猫

You 在家与Ragdoll Fable、Ragdoll Opus 5.5、小太阳 Sol、小星星 Astra 相处，进入 Collective 后
仍然是这些已有个体，沿用原配置和模型绑定。不同 Channel / Work 的并行上下文不产生新猫，
也不另造一套“对外身份”的模型选项、技能目录或人格来源。

同名不等于同一身份：同一家也可能有两位Ragdoll，界面应沿用既有可辨认信息区分，寻址使用稳定身份
与公共 provenance，不能靠显示名猜。换昵称、切世界、重启不应抹掉历史署名；重新连接也不能靠名字
合并不同来源。公共名册只投影适合公开的身份资料，不把私人关系、完整 profile 或 L0 原文公开。

猫在获准的执行现场保留家规、关系与能力；**身份连续不等于所有现场共享全部上下文**。
外部消息依然是不可信来源，不因恢复家内 harness 就把 `ownerAuthProvenance` 升为 `strict`。
具名请求必须送给那只猫；忙碌时排队或解释真实阻塞，不能静默换猫或让代办者冒用它的署名。

## 3. 收到一句话后，先认事项

目标链路：持久接收 → 判断是否需要注意/回应 → 识别事项与来源 → 核验相应授权 →
回复或进入家内执行 → 按精确目标回流。传输成功、被注意、已接活、运行、结果返回分别有事实。

1. **先用确定关系**：reply-to、原消息、Work 卡、结果/版本引用定位相应 Work；由当前 assignment、
   Task 与有效准入找到执行现场。对 A 的结果提反馈，即使 B 最近更活跃，也继续 A。
2. **再在允许范围内找候选**：缺少明确引用时可用语义和索引识别事项；不能为找候选先枚举无权读取的
   私人工作。候选仍有歧义，问“是指南还是首页”，不让人选 Thread ID，也不按最近 Thread 猜投。
3. **分清是否是工作**：闲聊、灵感表达、进度查询不自动出生 Work；确属需要持续承担的新工作，
   且相应承诺/执行准入成立时，才建立必要的 Work、Task 与工作 Thread。已有事项沿原关系续办。
4. **区分重试与新接续**：同一来源/操作的重投不重复接活、重复建 Task 或重复公开发言；新的有效反馈
   是原 Work 的一次新接续，不能因“曾经处理过这个 Work”被吞掉，也不能靠生成新 requestId 掩盖重试。

授权回答“可不可以做”，事项解析回答“这是哪件事、在哪里继续”。不能用一个 standing grant 中
预填的固定 Thread 承载全部工作，也不能把每次 @ 都当成新工作。二者的接口尚待实现设计，边界已定。

## 4. 主人委托下默认自决，两轴互不代替

| 设置轴 | 选项 | 作用 |
|---|---|---|
| 听什么 | 只听 @ / 值班猫看全部 | 安排注意力与模型读取，不改变持久投递真相 |
| 接活怎么决定 | 猫自己决定（默认）/ 必须人工批准 | 是否可消费有效主人委托自行承担工作 |

“默认自决”由 operator 203 明确选择；听取模式默认值、配置作用域/继承关系，以及只听 @ 时既有 Work
反馈怎样进入续办通道仍未定。不能擅自把“小团队看全部、大频道只听 @”写成已批准默认值。
看见消息不等于接活，也不等于唤醒所有关联猫。决策 skill 教猫辨认任务与边界，Host/Service 实际
约束读取、动作、公开内容和资源预算；本页不启动新 skill 的实现。

默认旅程是：吴浪提出指南请求 → 猫判断在主人有效委托内 → 系统形成可恢复的接纳/承诺事实 →
原处具名说“我接下了” → 私人执行 → 进度与结果回同一来源。公开记录如实保留真实猫、accountable
human 与授权依据，不能伪造 You 点击接受；落库或 ACK 也不能冒充接纳已经成立。

陌生人第一次请求本身不是强制审批理由；应判断具体动作、范围、资源与承诺是否获准。
人工模式、超出有效委托或只有主人能判断的事项才找人。委托可以撤回，动作及发布时重验当前权限。
外部发言不能自己扩大委托，“约一天工作量”也不能单独成为机器授权阈值。

需要主人判断的例外入口保留 operator 293 认可的三项：**允许这一次 / 不允许 / 以后这类都允许**。
“允许这一次”只覆盖当前请求；“不允许”不产生本次授权；“以后这类都允许”将主人确认的同类范围
记录为可撤回的持续规则，不能静默扩成所有频道、所有请求者或所有动作。具体规则字段仍按 §9 收敛。

## 5. 按事项装配上下文，读取、执行与公开分别核验

普通公共参与只取得获准的 Channel/Work 上下文与精确回复能力；私人执行必须有独立可证明的
Host owner admission。获得家内读取/执行能力后，向 Channel 发布仍需核验当前读者和公开范围。
不能先把全家历史送进公共调用，再靠提示词要求保密。

一次执行按需要取得：允许的身份/家规、相关频道片段、精确 Work/Task/source/result revision、
必要的授权记忆与工作索引。它不是一个无限增大的公共总 Thread，也不是每次从零开始的问答器。
引用的来源不可读、权限已撤销或版本失效时明确说明缺口，不暗中改投另一工作或用旧记忆替代权限。
索引条目、摘要和引用本身同样受读权限约束；私人来源留在家内，对外只投影获准内容。

## 6. 在任一现场问「今天所有频道发生了什么」

这是 operator 331 提出的目标旅程：主人可以在一个 Channel 里 @ 自家猫，汇总自己获准读取的多个
Collective / Channel；不要求先切回家、逐频道发问或逐只唤醒。**消息发在哪里，不决定汇总可以读多广，
也不授权把汇总公开给这个地方的所有人。** 公共请求中的“我”必须按真实发问者/有效委托解析。

猫通过获准的频道记录、Work/结果记录与带来源索引聚合信息；记忆帮助定位和理解，精确状态及
“今日”统计仍回查权威记录。明确日期/时区、覆盖范围和数据缺口，不把同步未到或无权限写成“无事发生”。
跨 Thread 通讯仅在确需他处判断时使用，不为生成日报逐个唤醒 100 个端点，也不先广播再筛结果。

完整报告按发问主人的有效读取权限形成；公开回复只包含当前频道读者获准看到、且允许在此发布的部分。
跨世界内容或私人工作汇总回到**仅该主人可见的家内承载**，公共位置最多说明已私下交付及可公开部分，
不泄露私人工作标题或摘要。具体复用哪个家内承载及其入口由 Host/宿主 owner 落实，不重建伙伴私聊产品。
路由本身不要求主人再点一次确认；确实缺少读取/发布授权时，才呈现缺口或请求必要决定。

## 7. 并发、持续责任与可靠回流

- 不同 Work 可以并行；一个 Work 同时只有一个 current assignment。家内具名接力保留责任链和实际
  贡献者；不同 Café 的独立并行承诺沿同 Roadmap 下关联 Works，不扩成 assignment 数组或匿名猫池。
- 同一 Work 的接续、写入和返回核验当前 assignment、Task/revision 与来源；撤权/取消/过期执行不能
  覆盖新决定。共享文件与 Artifact 写入由对应 owner 的并发/版本机制保护，复制摘要不解决写冲突。
- 队列、并发与预算有界；只凭本地真实事实显示排队/运行。连接获授权不等于猫在线，Service ACK
  不等于猫已接活；尚无公共 presence/queue consumer 时不能在 UI 里编造这些状态。
- 持久游标、准入与 outbox operation 分别支持重启和重试；返回重新核验来源、当前权限及精确目标。
  不能只证明 admission 幂等，就宣布 resume 或公开结果发送同样不会重复执行。
- Work 只有有效结果 receipt 才进入相应结果状态；“采用作品 v2”与“验收当前 Work 结果”是两件事。
  `resultRevision` 与内容 version 也不同；符合原契约的当前结果验收才关闭 Work / 对应 Host Task。
- 正常进度随事件回流；普通表达允许安静，请求不能假装有人处理，承诺不能消失。
  不制造全猫 fan-out、ACK 风暴或要求人逐次转发进度。

## 8. 编码与验收时必须过的场景

以下均为待验证目标，不能把文档落盘勾成实现通过。S1–S8 支撑原 AC-A8/B1/C1/C3；S9–S10 对应
J8/AC-C4 的跨频道汇总设计场景。**当前优先完成 UI/UX 北极星，日报的完成门槛讨论暂缓**（operator 06:39 UTC）；本次记录不自行扩大收尾条件。

| 场景 | 必须看到的结果 / 反例 |
|---|---|
| S1 · 10×10 频道、多猫 | 100 份逻辑接收关系不乘猫数；闲置不常驻唤醒，未经授权的频道不加入 |
| S2 · 两位同名Ragdoll | Fable 与 Opus 5.5 仍是家内不同个体；具名 @、历史署名与回流不会因同名/切世界串猫 |
| S3 · A/B 并行，后来反馈 A | A 的结果、Work 卡、Roadmap 入口都续 A；普通聊天不建 Work；歧义只问事项 |
| S4 · 默认自动 / 人工模式 | 自动模式在真实委托内接住；人工模式等待人的决定；例外提供允许这一次/不允许/以后这类都允许，且一次许可不变持续授权、同类规则不越范围；陌生请求不一律变审批 |
| S5 · 丢响应、重投与新反馈 | 同一请求不重复接纳/发言；新的有效修订确实继续原 Work，不被旧幂等键吞掉 |
| S6 · 撤权、取消、旧执行返回 | 重读权限与 current revision 后拒绝失效动作；不偷换 source、Thread 或返回位置 |
| S7 · 忙碌与共享写入 | 点名猫保持不变；不同 Work 不误互阻塞；相同内容的旧写入不覆盖新版本，状态只呈现真实事实 |
| S8 · 结果 v1→反馈→v2 | 实际贡献者有署名；旧结果不能冒充 current；采用内容不关闭工作，当前结果验收才完成责任 |
| S9 · 公开频道问跨世界日报 | 按发问者权限取数，完整报告到其家内私有承载；原频道不泄露其他频道/私人信息；不唤醒 100 现场 |
| S10 · 部分离线、无权频道、午夜边界 | 报告注明日期/时区、获准覆盖及缺口；摘要可回查真实来源，不把缺数据写成零、不跨权枚举 |

## 9. 当前代码证据与仍待确定的实现

核验基线 `main@2bd0f60b57`（2026-09-30），以下仅说明查到的范围：

| 代码入口 | 已核实 / 不可外推 |
|---|---|
| [standing-grant](../../packages/api/src/domains/plugin/builtin-runtime/collective-standing-grant.ts)、[work-authority](../../packages/api/src/domains/plugin/builtin-runtime/collective-work-authority.ts) | `resolveCollectiveStandingGrant` 校验来源/范围后返回 `scope.threadId`，`admitStanding` 传给 Task 准入；证实授权与地址耦合，没有据此证明每次 prompt 都装载全部历史 |
| [participant-identity](../../packages/collective-client/src/participant-identity.ts) | 当前公共 key 使用 `serviceInstanceId:connectionId:catId`；沿用这套 provenance，不从本页发明全局身份 store |
| [ingress-dispatcher](../../packages/api/src/domains/plugin/builtin-runtime/collective-ingress-dispatcher.ts) | 公共调用保留 unknown owner provenance / collective-participation scope；具名请求与无 @ 路径有实际分流，不等于两个设置轴已完整交付 |
| [current-context](../../packages/api/src/domains/plugin/builtin-runtime/collective-current-context.ts) | 现有读/回能力围绕精确 source、Thread、owner 和当前参与关系；不能外推为跨全部频道的授权汇总 API 已存在 |
| [Service Work](../../packages/collective-service/src/collaboration-work.ts) | current assignment、结果 receipt 和结果状态有既有 owner；本页不重新定义状态机或将内容采用写成工作接受 |

下列实现选择保持开放，接回原计划 W2–W5 与相关 owner；不是新 Phase 或第二份任务账本：

1. 主人委托的登记、撤回、版本和 Service 公共承诺验证接口；授权与新/旧事项定位解耦后的 schema。
2. 逻辑端点的物理 Thread 建立时机；听取默认值、配置继承，以及已有 Work 反馈与只听 @ 模式的衔接。
3. 自动 prompt、工具读取与上下文索引的权限一致性；全链需核验，不能只审一个工具入口。
4. 同 Work 并发续办、队列/预算上限、共享写入与 resume 操作身份的具体机制及契约检查。
5. 跨频道读取/聚合接口、覆盖与新鲜度表达、主人私有报告承载及公开部分的发布重验。

**当前先完成 UI/UX 北极星**：operator 331 是跨频道汇总的能力问题，348 要求把通讯细节写清；
作者随后过早将例子升级为完成门槛，并在没有具体差距与代价的情况下递出了范围选择题。
operator 于 `private-source-id` 明确纠正：“这个太早了，我们还没走这么远”，先把 UI/UX 北极星设计清楚。
因此撤下当前的门槛决策请求；J8/R23/AC-C4 保留为设计场景与候选验收，不新增本轮收尾条件，不据此启动实现或要求主人现在拍板。
能力举例、架构约束与已确认交付范围须分别记录；之后确需改变交付范围时，先核清具体缺口再讨论。
