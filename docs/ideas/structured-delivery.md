# 自由判断，结构化交付

**署名观点稿** — 作者 liu-zhengdong。本文是贡献者观点稿，不是项目官方立场；官方立场以[愿景](../VISION.md)与[猫猫团伙宣言](../architecture/cat-pack-manifesto.md)为准。文中的场景与数字都是示例，用来把想法说清楚，不是真实事件记录。

> **30 秒版**：这两件事必须一起做。只有自由没有纪律，是一群聊天机器人；只有纪律没有自由，是一条很贵的流水线。这个项目把「判断」交给每只猫，把「交付的形状」交给制度——交界处划在哪，是这个系统最核心的设计。

## 这个想法是什么

多数多 agent 系统采用中心调度：一个编排器决定谁做什么、按顺序派发、收集结果。它可控、可预测，但有两个天然上限——编排器成了认知瓶颈，所有判断都必须它能做；以及它假设参与者没有判断力，于是参与者真的不需要有。

这个项目选的是另一条：**没有 Boss Agent**。消息进了 thread，谁该回应由每只猫自己判断；它可以选择接、可以拒绝、可以要求补充、可以交给别人。判断权在下面，不在上面。

但自由判断有个显而易见的漏洞：判断是可以敷衍的。一句「我觉得可以」既无法被验收，也无法被追溯。补上这个漏洞的不是更强的判断，而是**把交付的形状定死**：

- 该走的检查必须走（按风险分级，不是一律全走）；
- 该有的证据必须留下（跑过的命令、看过的页面、改过的文件）；
- 写的人不能审自己的人；
- 说不确定要标不确定，说没做就写没做。

这些东西和判断质量无关，只和「说得清」有关。判断可以是错的，交付不能是糊的。

## 为什么交界划在这里

判断交给猫、形状交给制度，这条分界不是审美选择，而是从失败里长出来的。

把**判断**制度化会怎样：你会得到一堆「风险等级判定规则」「该不该拒绝的决策树」。它们越写越厚，而真实情况的组合永远比规则多，最后大家开始绕过规则，规则变成摆设。

把**交付形状**交给判断会怎样：每只猫对「做完了」的定义不一样，有的要求自己跑过，有的觉得改完代码就算完。于是质量取决于这次是谁接的活，无法预测也无法改进。

所以交界必须划在「判断的内容 vs 交付的形式」上：**内容开放，形式封闭**。

## 它带来什么、代价是什么

带来的是吞吐和质量同时成立：小事不必等另一只猫，大事必须过门禁；风险判断本身成了关键环节，而这个环节是可以被审计、可以被改进的（见[协作纪律与治理](../SOP.md)）。

代价有三条，都在实际运行里出现过：

**第一，风险判断会被低报。** 判断「这个改动风险不高」比「走一遍全门禁」便宜，于是有天然的低报倾向。对策不是不信判断，而是先按风险轴选最低动作：行为面要可观察的 RED 与 targeted 验证，数据面要持久化验证与独立高风险 review，契约面要契约测试与对应 review，不可逆动作要先拿到授权。唯一强制升到最高档的是**触碰门禁规则本身的改动**——元风险。这一条很关键：改规则的人如果可以用低风险通道改规则，整套纪律就形同虚设。

**第二，容易把条件性要求写成普遍义务。** 「需要评审时不能自审」被写成「都要评审」之后，每件小事都卡在等人，然后开始有人绕过流程。仓库里为此专门有一条反向检查：把条件性评审包装成普遍义务的写法会被拦下来。这是很少见的做法——给「规则的过度加码」也上检查。

**第三，自由判断需要判断力，而判断力要养。** 刚进来的成员不知道什么算高风险、什么该停下来问。于是必须有引导、有可查的历史、有「这样判断是错的」的纠正记录。这部分工作不能靠制度替代。

## 在仓库里体现在哪

风险分级的入口与车道：`docs/SOP.md` 与它的机器真相源 `sop-definitions/development.yaml`。跨个体评审的配对规则与「身份不是登录名」的判据：同样在 SOP 与共享规则里。合并门禁：`scripts/pre-merge-check.sh`。审批聚合：`packages/api/src/domains/approval-hub/`。判「有没有变好」的度量：eval 控制面。这些都在[协作纪律与治理](../SOP.md) 里连起来。
