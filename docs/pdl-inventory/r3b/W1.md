### 之前／之后的数据流

1. 之前：每次键入 → host input 改变 → chat source 改变 → update render；输入处理本身又 render。

5. VM 读持有的数据；工具配对按消息来源派生，未变消息的 item version 和 DOM 节点保持不变。

### 前后流向

1. 前：宿主 render → 全模型重建／深比较；工具 hook 在挂载时预读。
2. 后：来源变化才 push；console 持有完整数据，VM 延迟读取，并在一次投影后对 needed 做差异。
3. 出现／重现／重连 → 拉该来源完整状态；原周期或既有事件只在需要时刷新。
4. 离开 → 停周期／数据推送，保留 full base；回拉按 id 保留未变记录的引用。
5. 只有未结束消息的增量继续积累；通知／命令走独立到达通道，未接出口单列。

### 前后数据流（五行）

1. 之前：host 任一次 render → 重建 chat／sidebar／所有 owner 包装 → console 深比较整棵对象。
2. 之后：原始来源引用变化 → 只发布变动来源 → console 按 id／引用合并到 held snapshot；VM 只读它。
3. 投影：beforeRender 开始记录 held 读取 → onRender 收集 needed → 与上一份集合做差异。
4. 读取：新增来源读一次／开始自己的既有周期；离开停止读取、保留数据；未变来源不因 render 再读。
5. 刷新：来源自己的动作／事件刷新自己；重现或重连重新读当前需要的来源；回执未变记录保持引用。

## 召回错误的根因与验证

出现 null 的是消息的 **meta 投影**，原始线程和消息仍在 held 数据里。历史消息的工具事件可能不带召回数据，召回次数来自真实 workbench.recall.events；该 owner 刷新时会暂时推 `{load:'loading',page:null,events:[]}`。此时那条回复没有执行记录或召回计数，chat-models.ts 按现有规则给 meta=null，这是正常空数据状态。

切到设置空间后，对话层被引擎隐藏并缓存。此前应用的原始数据接收点更新了 held snapshot，却没有给这些留存层发数据版本失效信号。返回时消息外壳未变，引擎可能复用旧节点；里面仍有旧的“召回”按钮。该按钮调用 OPENERS.recall，后者重新读取新投影的 item.meta.recall，于是读到 null。

新测试按真实空间切换走 `OPENERS.space(settings)` → 召回 owner 推 loading 空页 → `OPENERS.space(cafe)`：返回时不会留下旧按钮；真实召回记录回来后按钮重新出现，点击仍选中原 reply-1 的分组，recallExpected=1。测试也保留 host model builder 的禁止调用断言。

本轮只在现有应用接收边界补数据版本通知。数据没有变化不会增加版本、不会触发额外 render；引擎的缓存、局部更新和滚动所有权未改。纯投影测试宿主 `__tests__/owner-console.ts` 仅补上生产引擎已存在的 navStale API 桩。
