# 项目能力在新设计中的落点清单

本清单供 lang 确认能力取舍和落点。本轮只写清单，不改原型、不写迁移代码、不改真实接口。除注明“已定”的 r105 决定外，所有落点均为建议，尚未批准加入 PDL。旧设计的组件和定制交互只归 v2 主题，新设计不保留其 JSX、兼容分支或位置状态。

## 基线和读取范围

- 当前原型基线：`design-accepted-r105`，提交 `b60115a7f797af3ea91cc6ce0d9f2ac5e2ed9fd0`。交接依据是该 tag 的 HANDOFF 第 5 节“lang 2026-11-03 的迁移决定”；规则取该 tag 的 spec/engine.md 和 spec/library.md。
- 项目证据：当前 worktree 的业务源码来自 `42017e0cea07e3e259e7fb183be70433f05e131c`；本轮开始 HEAD 是上一轮文档提交 `68088dff1cc5fdad13931fc57580463558669a5a`。文件行号均对本 worktree 的源码核对，未读取 *.local.js。
- r105 契约仍为 70 个 VM，动作从 r104 的 325 个变为 319 个：去掉 8 个旧动作，新增 download、logsExport。上一轮 TSV 保留为 r104 盘点快照，不把本轮的拟增字段伪装成已存在。
- 此表覆盖上一轮“需要新组件或样式的候选”全部类别，并补查人物/画像/事件/实体各 owner、进化准备/探索/变更、云恢复、运行时、语音/会议、详细审阅、插件表单，以及委托、运行时问答、评估修复、页面授权等同类能力。另列已定通用能力核对项和仅属旧设计的交互；不把这些都算成“原型没有的组件”。
- 核对顺序是用户能做的动作、对应读取/写入 owner、r105 容器/组件能否表达。源码里只有设计样例的能力明确排除；仅有后端接口而尚无主站入口的能力明确注明。

## 字段 动作和落点记法

- “现”是 r105 已有 VM/动作/登记点；“+”是拟增加的字段、实体登记或领域动作。花括号是字段清单或参数示意，不是新文件、新配置或新一层。现动作若增加参数或 owner 分派，同样写明“拟”。
- VM 扩展放回已有应用根；不增加 service/manager/adapter/registry。既有 ENT/OPENERS/动作登记点足够；各真实 owner 的身份、权限、版本、幂等与回执约束在应用绑定中保留，不把技术 id 铺进默认界面。
- 表中“已存在的实际请求”不是“已经绑定到新契约”。例如 pcfCatalog 是组件目录演示 VM，产品插件表单实际落在 ext.sel.config.form；本表使用后者，不把 catalog 演示实例搬进产品。
- a：建议进入指定的已有页面、区域或插槽，只用已有组件组合；b：有意省略并写理由；c：第 4 类独立 frame；d：现组件确实不能表达该能力，先回原型补同一个组件。
- b 项若省略的是旧交互，相关业务能力仍在对应 a 项保留；不会因为换画法连同能力一起删掉。新设计的领域动作和来源引用共用，旧交互只归 v2 主题。
- 加载、错误、不可用、过期与部分可用都复用 r105 的 viewState/notice/fieldErr；当 owner 没给权限、来源或可执行动作时，只呈现相应状态。不以本地“看过/关闭过”决定生命周期。
