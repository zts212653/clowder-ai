F311 · Capability Evolution Workspace
✓ 终态 Phase 已合入 main

不是“进化一个东西”，而是造一座
能持续进化任何能力的工厂

用户只要说一句“我们来进化 X”。后厨自动完成建制、取证、评估、归因、审批、写回、新鲜复验和退役；用户能看懂、能批准、能撤销，但不用被迫当标注员。

终极产品承诺：今天纠正过的事情，明天不再重新交学费；使用系统的过程，会积累成属于用户自己的能力资产。
反脚手架契约每个 Phase 都是最终产品永久保留的器官。没有样例 Harness、临时 adapter、影子状态机，也没有“Demo 成功后推倒重写”。

用户眼中的一条完整旅程

PHASE 1一句话开工Program 出生，目标、价值主人和经济账可见
PHASE 2系统长出眼睛从正常工作里获得新鲜 bit，不加标注任务
PHASE 3拿尺子查原因分清是执行、Harness、尺子还是眼睛坏了
PHASE 4批准后才动手真正写回、回滚、复验，并决定保留或退役
PHASE 5换对象也能用记忆、Skill、猫画像、外部系统共用一套工厂
PHASE 6工厂也会学习立尺、开眼、归因这些器官自身也能进化
PHASE 0 · 已完成

先立宪法，再施工。已经冻结：F311 是薄控制面；F299 是唯一 invocation trajectory 面；F246 是唯一 Approval 入口；F307 是唯一 Workspace 宿主；版本、证据、写回与 outcome 仍归原 owner。后续任何 Phase 都不能借“先跑起来”再造一套。

每个 Phase 到底交付什么

🪪
PHASE 1

建制与可见

给一次进化办出生证，并把工地打开给人看
我们建设

Durable Evolution Program：对象、单一 claim、经济页、双证、四角色、owner refs、生命周期与当前阶段。

用户获得

任意聊天页说一句话即可启动；Workbench 实时看见进度、阻塞和下一步，正常路径零表单。

完成标志：Program 从创建起 TTL=0、重启可恢复；API、猫动作和 F307 UI 读取同一份真相。
为什么不是一张 Demo 卡片？

因为第一天就落正式事件流与正式 Workspace surface；卡片、MCP 和 API 都只是同一 canonical truth 的投影。

👁️
PHASE 2

开眼与取证

让系统在真实工作里看见发生了什么
我们建设

接入 F299 trajectory、日志/指标/爪感差/采纳撤销/外部 evidence；在 F192 注册事件、时间、配额触发。

用户获得

不用额外打标签；正常使用、取消、修订、复用本身就成为有来源的新鲜信号。

完成标志：Workbench 能回答“眼睛接了什么、还缺什么、何时评估”；F311 只持 ref，不复制证据 payload。
谁真正保存数据？

轨迹归 F299，各类业务信号归各自 source owner。F311 只保存 join key、consumer 与来源引用。

🔬
PHASE 3

评估与归因

不只说“变差了”，还要弄清到底哪里坏了
我们建设

复用 F192/F267 的 rubric、baseline、measurement 与 validity；支持执行/Harness/尺子/眼睛四层归因和 2×2 换尺复判。

用户获得

看到人话解释：证据够不够、有哪些竞争归因、为何现在应该改或暂时不改。

完成标志：证据不足可以诚实输出 unresolved / insufficient / incomparable；没有 intervention card 与双 falsifier，不能进入审批。
为什么要“新世界”证据？

被优化器看过的样本只能帮助归因，不能证明泛化；晋升必须使用未暴露的 sealed 或 time-fresh holdout。

🛂
PHASE 4

受治理写回、复验与代谢

有判断不等于能乱改；批准、写回、复验才叫闭环
我们建设

真实 change/adopt/invest 才进 F246；asset owner 写回并给 receipt；F266/F313 关闭 outcome；F311 编排 lineage 与决策。

用户获得

能批准或拒绝真实改变；能看见版本、回滚与新鲜结果，并做 keep / tune / rollback / sunset / no_change。

完成标志：首个真实 E0 Program 从一句话走到 merged+loaded 后的新鲜 outcome；“有 proposal / 有 merge”都不算已经进化。
首个对象在这里扮演什么角色？

只是一条真实生产验收旅程，不预设对象、不定义 schema、不独占 Phase；没有合格目标时绝不造样本。

🔌
PHASE 5

多对象联邦与外部适配

证明这是通用插座，不是某个对象的专用流水线
我们建设

同一无对象特有字段的 Program schema，承载至少两个异质家内对象，再接一个外部托管对象。

用户获得

记忆、视频 Skill、猫画像、per-cat Harness 或外部系统，都能在同一个 Workspace 中被治理和比较。

完成标志：F307 统一编排多个 Program；外部部署、签字、回滚与 outcome 可审计，但业务真相仍留在原 owner。
怎样防止“大一统平台”吞掉所有系统？

Adapter 只声明能力与 ref resolver；版本、审批、轨迹、变更和结果都不搬进 F311。

🧬
PHASE 6

进化机制本身

不只让学生进步，也让眼睛、尺子和老师学会变好
我们建设

把立尺、开眼、归因、Eval 设计和 Program 编排本身作为二阶 Program；沉淀可版本化、回滚、退役的 skill/heuristic。

用户获得

随着真实循环增多，系统不只积累能力，也逐渐学会怎样更可靠、更省钱地进化能力。

完成标志：产品能力必须接通；但未自然积累 ≥K 个可比较案例时，只能写“效用未实证”，不能拿 rubric diff 冒充 GT。
二阶 GT 是什么？

不是“我们改了 rubric”，而是这套新尺子后来是否让一阶 Program 在真实下游表现得更好。

贯穿所有 Phase 的修路车道

🛠 Owner Contract Repair Lane
它不是产品 Phase

某个 join 出故障时，F311 记录 exact owner、live case 与 source ref，再把修复交回对应 owner thread。修好后带 receipt 接回来；一个 join 坏了只阻塞自己，不让 F311 变成全家 bug 修理队，也不让整座工厂等全家修完才开工。

架构师最关心的所有权边界

F311 真正拥有的东西

  • Evolution Program 的 identity 与 lifecycle
  • 当前 stage / schedule 的编排投影
  • Owner refs、双证 refs 与 gate 状态
  • AssetVersionRef 与证据→干预→结果的因果 lineage
  • keep / tune / rollback / sunset / no_change 的编排历史

必须留在原系统的真相

  • 轨迹：F299；评估与尺子：F192 / F267
  • Approval：F246；dispatch/outcome：F266 / F313
  • 真实 mutation、版本与 rollback：asset owner
  • Workspace layout：F307；业务 evidence：source owner
  • F311 只联邦读取，禁止第二 Store / Queue / 状态机 / 轨迹页

什么时候才允许说“F311 做完了”？

真实闭环
一句话 → fresh evidence → Approval → owner 写回 → loaded 后新鲜 outcome
治理闭环
observe/insufficient 零卡；无批准零派工；target drift 令旧批准失效
生命闭环
重启可恢复；rollback/sunset/no-change 可执行；外部对象也能审计回滚
