# PR #1745：Windows DSH 启动拒绝与改发确认

## 现象与证据

安装版的一键检测创建了 DSH 角色，但 `@all` 没有它的回复；单独 `@dsh` 时，实际回复来自 Codex。用户选择的处理原则是：允许改发，但发送前必须确认实际接收者。

本机安装版 API 日志明确记录 `Cat "dsh" ACP startup failed; marking it unavailable: secret_dsh_patch_changed`。只读回查该会话，DSH 的消息数为零且不可路由，其他角色可路由。检测到已安装不等于运行时启动成功。

DSH 启动保护对 `secret-dsh-plugin.mjs` 进行精确字节哈希校验：审核值为 `c34e9b909d42d44f52d4742fcd7e94679cacd65e26f8743403121521628c8901`。本机源码检出、暂存产物和安装目录中的文件均为 954 字节、含 24 处 CRLF，实际哈希为 `c439aa416886b634847c1ac281d6947a5231818ac5f26e0cb5db00722e9d3aba`。只把 CRLF 规范成 LF，哈希即与审核值完全一致。修复前，已有 `secret-dsh.test.ts` 三项测试均报上述错误。

公共会话原有路由允许跳过不可用角色并选择可用对象；输入框预览和实际发送分别请求路由，可能观察到不同状态。安装日志可证明 DSH 启动失败，但现存截图不能单独证明页脚与实际回复不同所涉及的全部时序。

## 修改

- 为受校验脚本声明 LF 检出规则，并在运行时资源暂存时规范 CRLF，覆盖已有 Windows 检出目录。运行时仍做原有完整哈希校验，不放宽权限、信任或篡改检查。
- 普通消息明确指定不可用角色时，服务器在写入消息和队列之前返回 `409 ROUTING_CONFIRMATION_REQUIRED`，包含不可用角色和当前实际接收者的名字、昵称及内部 ID。
- 前端复用已有确认弹窗。取消不发送、保留草稿；确认后携带实际接收者及原幂等键重试，并按精确目标入队。所确认角色随后不可用时，不再静默换成第三个角色。
- JSON 和图片 multipart 请求均支持确认；Whisper、Live、Message Bundle 保持各自的精确收件人契约。
- 非作者评审另复现「预检时 DSH 可用、入队前失效」仍静默换人的问题。具名目标从本请求预检成功起关闭会话回退，之后失效不调用替代角色；保留正文来源及其原子胜者复用规则，不放宽 Queue 的 exact/prose 围栏。相同消息重试沿用已入队对象，`@all` 的成员变化也不改写原消息；不同确认对象继续被幂等身份校验拒绝。空 `mentions` 数组按未提供处理，不能跳过正文点名校验。
- 原始消息正文保留，内部 ID 继续用于路由，界面确认显示角色名及昵称。没有配置或历史迁移。

## 验证与边界

- DSH 保护测试：修复前 3 项失败，修复后 3 项通过，包含篡改拒绝、旧文件保留和并发创建；可移动运行时布局测试 2 项通过。
- 真实 Fastify 消息 API、AgentRouter 和 InvocationQueue 回归：确认前无写入、确认后目标精确、重试幂等、目标再次失效、队列执行前失效、multipart、DSH 恢复后具名和 `@all` 路由。
- 发送 Hook 回归：等待确认、取消、图片和引用保留、原幂等键保留、第二次拒绝不自动批准。
- 浏览器隔离验收使用当前工作树的生产 Hook 和 ConfirmDialog，连接真实消息 API 与内存队列；取消保留草稿，确认后只入队 Kimi，恢复 DSH 后具名消息只入队 DSH。模型调用桩会拒绝任何真实调用。
- 本轮未重建或替换用户的安装包，未运行真实 DSH 模型请求。最终 EXE 的真实模型和安装回归仍须使用包含本次提交的新包验证，不能把已有安装版当作修复后的产物。

验收产物位于任务 artifacts 的 `pr1745-ci-develop-20261030/routing-preview`，含确认截图、浏览器回执与停止回执。临时端口为 4336/4337；不连接生产 Redis，也不使用原生客户端 HOME。
