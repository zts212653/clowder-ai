### 怎么迁（三条原则）

1. 插件的业务逻辑**整体搬走、不重写**。
2. 只改「和 Host 打交道的那一圈」：Host 把这一圈做成通用接口；插件仓让 SDK 包住它，插件改用 SDK。
3. Host 为某一个插件单独写的接口 / 卡片 / 工具 / 管理，一律收敛到通用机制，不原样搬。
4. **「整体搬走、没改」要可验证**（operator 09-21：风险只在插件与 Host 之间的桥；搬过去的逻辑没改，上游 review 只需看边界）。
   跨仓搬迁在 diff 里是一边删、一边增，reviewer 看不出「没改」，所以：搬迁与边缘改动分开提交（先纯搬、后改边缘）；附一份机械对照——
   逐文件比对 Host 删掉的与插件仓新增的，列出全部差异行，它们应当恰好等于「只改的边缘」那一列。PR 描述里写明：核心改动 = Host 补的接口 + 这份差异清单。

### 顺序与完成标准（同一个 PR，不留 followup）

1. Host 做 A–E → commit。2. 通知插件仓做 a–e。3. Host 逐包做 F、G，按由易到难的波次：① 视频、微信公众号、微信会话读取、enterprise workflow → ② 7 个 connector 与 ChatGPT Pro（同一条消息链路）→ ③ github 整簇 → ④ collective、GenOffice 的 docx 生成 → 飞书纪要同步随插件仓改造完成时删。每一波都是：装包 → 跑通 → 确认不双跑 → 删，分支始终可用。4. 收尾 I（自动安装内置插件），并由 operator 定 H（已有数据迁移还是忽略）。5. 插件仓发布 contract / SDK → Host pin → worktree 验收。

**验收不等 npm 发布**（operator 09-21）：每一波的「装包」用插件仓**本地打出来的包**即可——Host 的插件管理本来就支持本地目录、本地压缩包和上传安装
（`PluginManagerPackageSource` 的 `local-directory` / `local-archive`，`/api/plugin-manager/plugins/install/upload`）；两仓迁移清单的依赖顺序也是「先打包产物、后发布」。
唯一例外是 **contract 包**：Host 在构建期依赖它（`packages/api/package.json:62`），开发期可以用本地 tarball，但 Host 这个 PR 合入上游之前必须换成已发布的版本号。

**完成标准**：上表各项从安装包装上并能用（ChatGPT Pro 为「与现状一致」）；Host 与 SDK / contract 里只为某个插件服务的后端代码、接口、路由删净；留下的只有 C2 表里那些定制前端。

## 3. 不进契约的（随插件整体搬走，插件内部闭环）

**判据（operator 09-21，`…004255`）**：Host 为某一个插件单独写的通知卡片、单独写的工具，都是「特殊逻辑」，不合理。

**场景判据（operator 09-21，`…004288`）**：假设内网用不了 GitHub，或者对接的是 gitee，或者没有 git 只有 svn——
这时 Host 里还留着的、和某个具体能力强绑定的东西，就一定不合理。按它量过一遍 GitHub：若 tracking 留在 Host，

具体怎么往平台发（普通 / 富文本 / 流式编辑 / 表情回执 / 批次结束）、入站媒体下载、去重、群白名单；
