# Console Dev — 前端开发范式

## 权威参考

**`docs/design/console-design-system.md`** — 唯一真相源。Token 名、组件模式、反模式清单、自检条目均在其中。

本 skill 不重复 Design System 内容，只描述「如何使用 Design System」的方法论。

## 适用范围

```
有视觉变化的前端改动：需求确认 → console-dev → worktree → tdd → quality-gate → request-review
无视觉变化的前端逻辑改动：需求确认 → worktree → tdd（跳过 console-dev）
```

## 核心范式

### 范式 1：层次靠背景色建立，不靠边框

Console 的视觉层次是通过 N 层递进的背景色差实现的，而非边框。每增加一个嵌套层，用下一级背景 token 即可区分。只在极少数场景（列表分隔线、表单控件、警告区域）才使用边框。

**决策原则**：先问「能不能只靠色差？」→ 如果不行再问「加 border-b 够不够？」→ 最后才考虑四边框。

### 范式 2：Token 优先，永远不硬编码

所有颜色、背景、边框、阴影必须走 Design System 定义的语义 token。具体 token 名称和用法查阅 Design System §2。

**决策原则**：改颜色时先查 token 表 → 找到就用 → 找不到就在 Design System 中新增定义后再用，不允许临时硬编码值。

### 范式 3：组件模式复用

Console 有固定的页面布局模式（双栏设置、列表页、详情页）和组件模式（内嵌卡片、代码面板、表单组）。新增 UI 前先辨识属于哪种现有模式，复用其结构和 token。

**决策原则**：新页面/组件 → 先找最相似的现有页面做参照 → 提取其布局骨架 → 只替换内容。

### 范式 4：设计先行于实现

任何有视觉变化的改动必须先对齐设计意图：
- **大幅改动/新页面**：出效果图（Pencil）→ 铲屎官确认 → 再写代码。铲屎官不在线则截图留存并等待。
- **小幅修改/Bug 修复**：在脑中确认符合 Design System 哪条规则即可动手。
- **批量视觉刷新**：先 grep 定位所有待替换模式 → 按 Design System 反模式清单逐条扫描 → 批量替换。

### 范式 5：自检闭环

代码写完后，必须经过两道验证：
1. **静态自检**：对照 Design System §7 自检清单逐条检查（无新增硬编码色、无多余边框、层级一致、术语合规等）。
2. **浏览器验证**：启动 dev server → 看 3 秒 → 感觉是否干净整洁 → 有无突兀元素 → 切暗色模式确认 token 适配 → 截图留存。

## 常见判断范式

### 「要不要加边框？」

大概率不要。先只用背景色 + 圆角 + 间距试试，够清晰就不加。
确实混在一起无法区分时 → 加 border-b 分隔线（不是四周边框）。

### 「该用什么颜色/token？」

1. 查 Design System §2 Token 规则表
2. 没有 → 查 `theme-tokens.css` 语义变量
3. 还没有 → 停下，新增定义后再用

### 「铲屎官说不够高级」

通常意味着：边框太多（换背景色）、间距太紧（增加 padding/gap）、元素不统一（对齐到组件模式）、颜色不协调（检查是否混用硬编码和 token）。

### 「加一个新页面」

1. 确认属于哪个布局模式（查 Design System §4）
2. 找最相似的现有页面做参照
3. 大改出效果图等铲屎官确认
4. 按 token 规则实现

### 「内嵌卡片 vs 平铺」

当一组配置/内容需要视觉分组时，用内嵌卡片（带色彩 header + field-bg body + 圆角）。
当内容是扁平列表时用平铺 + 分隔线。
不要两种混用，同一视图内统一。
