# 交互叙事：从看懂，到亲手参与

只需让陌生读者理解一个故事/机制时，先用[叙事清晰度](narrative-clarity.md)；本篇处理用户实际参与后的操作、交接与恢复。载体是漫画不自动需要交互，载体能点击也不自动证明业务成功。

按需用于参考产品拆解、首启或跨界面旅程。已有故事只改样式、普通业务点改，不加载本表重做设计。它提供观察与编排方法，不新增引导平台、业务状态枚举或固定幕数。

## 1. 从参考中学机制

按这一条链分析：**可见设计 → 它回答的用户问题 → 怎样起作用 → 在本产品里对应什么 → 最小验证**。

先分清手里的证据：完整视频、关键帧、作者分析、提案和真实运行记录各能支持什么。关键帧能显示构图与前后状态，不能单独证明动效节奏；无音轨不评声音；按钮被点过不等于业务成功。原作者的解释与自己的推断分别写。

| 观察 | 可借鉴的机制 | 迁移时要核对的事 |
|---|---|---|
| 首次出现的位置与常驻入口连起来 | 用户学会以后去哪里找 | 是否能从稳定入口找回同一件事，而非只激活某个进程 |
| 沿一次工作演示多个能力 | 每一步回答上一幕留下的问题 | 是否有可见的小结果解释协作价值，而非只多几条消息 |
| 探测后呈现可用项与选择 | 产品先完成环境中可查的准备 | 检测到、已登录、获授权、当前可用分别成立；自动发现不等于用户同意接入 |
| 欢迎、权限、付费同时给下一步指令 | 焦点与控制权会发生竞争 | 此刻谁是主动作，谁可稍后出现；不机械把所有权限都前置 |
| 点击“回去”后只打开承载进程 | 技术落点可能不同于用户的工作落点 | 当前对象、版本、可执行动作和返回路径是否正确 |

这些是设计问题与候选机制，不是对参考产品所有版本的故障结论。位置变化不证明误点，落在终端不自动意味着跳错；需要结合操作者意图与完整记录判断。

只请求“看看参考、聊聊能学什么”时，交付取舍与候选路径即可，不自动建原型、写 Guide YAML、启动服务或发布回复。已授权制作则继续相应制作技能，不把分析变成新的审批关卡。

## 2. 让理解与行动接上

每个关键交接回答：**用户此刻想知道什么；人/猫/系统做什么；出现什么可见结果；下一步凭什么开始。**

只在容易断开的地方补一张表，复用已有分镜或 Journey ledger，不同时维护三份故事：

| 用户此刻的问题或期待 | 谁做什么 | 用户看见/学会什么 | 下一步的真实条件 | 离开、拒绝或失败后从哪继续 |
|---|---|---|---|---|

示范中的脚本推进、真实操作的结果推进分开。此表是设计笔记，不是向 Guide Engine 添加字段；正式编排仅使用引擎已支持的契约，缺能力先明确缺口。

对长故事，动作解释过去怎样改变；对产品，用户的操作实际参与下一步变化。人不必先学会 Task、Artifact 或客户端等内部对象关系才能开始。

## 3. 示范到真实使用的交接

保留角色、位置与任务的连续性，同时明确从哪里开始是真实操作。

- 示范可以用真实组件和预设台词；不能声称真实模型已经执行，不能把演示成员直接当已接通成员。
- 环境自动探测完成后，按实际选择呈现自己的伙伴。0 / 1 / 多个可用连接是本案例需覆盖的分支，不是所有产品统一三分法。
- 只有一个真实伙伴时，仍可完整地开始。示范中的其他角色不要显示成可调用，也不要要求用户为了凑齐演示阵容购买或连接更多服务。
- 没有连接或用户暂不授权时，说清当前仍可做什么；回来后继续未完成的交接。未实现续接能力时，如实记为缺口，不用“下一步”按钮假装已恢复。
- 看懂示范、接通环境、完成首次真实交流分别验证。真实发送问候并收到回复，可以证明该次交流；不能外推成复杂协作或长期托付已验证。
- 第一次交流可以是用户自己的问题或寒暄，不强制创建任务、生产作品或进行多猫协作。只有承诺“做成一件事”时，才需要与该目标相称的结果。

## 4. 节奏也包含控制权、打断与返回

- 首次教学可以集中注意力；日常返回应让用户迅速继续，不为每次通知重新播放开场。
- 尽量让一个时刻有一个清楚的主动作。必要授权在使用对应能力时解释，支持拒绝与稍后；欢迎可以表达关系，不能提前宣告尚未发生的成功。
- 用户准备亲手尝试时，让他接过来。后续设置有稳定、可重看的入口，不必都排在第一句真实交流之前。
- “下一幕”不以所有按钮统一点击或固定秒数推进；真实保存、登录、授权需要真实结果，纯讲解可以按用户节奏翻页。
- 用户阅读、悬停、选择时保持目标稳定；新事件可以提示，不能让动作目标只绑定“当前第几行”。
- 返回要落在用户能继续处理的当前对象或产物版本。终端可能就是正确现场，须按工作判断；不要一概替换为首页、后台日志或旧截图。
- 某步总需很长解说时，先检查能否减少该步的实际复杂度；不靠不断加字幕代偿难用的交互。

## 5. 将设计走成一条真实路径

先选最能暴露当前未知的起始条件，不为“完整”遍历全部可能。拿首启举例，只有一个已登录客户端时，最容易看出示范队伍、实际伙伴与首次对话能否接好。

设计猫先用当前可用原型或产品走一次 golden path：记录操作、可见结果、下一步的依据，以及仍未走通的部分。只做分析时，提供建议验证路径，不声称已经走过。

需要验证什么，由 claim 决定：
- 想知道“看懂了吗”：让目标观众复述用途、去处与下一步；不能靠作者自己点头。
- 想知道“接通了吗”：读取当前连接/权限/操作的真实结果。
- 想知道“做成了吗”：查看与用户意图相符的结果；不把发出第一句话的耗时当全部价值。
- 声称可中断/续接：验证跳过、拒绝、失败或离开后，回到同一对象与正确阶段；这些是不同动作，不一概重播教学。
- 已有确定契约用检查/测试，运行健康用日志与指标；长期设计效用只有明确 consumer 与 keep/tune/sunset 决策时才另走评估。

对外解释保留必要状态与下一步，证据细表留底稿。不要把全部验收限制变成用户必须学习的内容。
