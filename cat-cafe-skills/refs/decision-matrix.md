# 决策权矩阵（漏斗模式）

> 来源：F-Swarm-4，2026-02-24 四猫+operator讨论确认。
> 可逆性维度：2026-05-08 三猫收敛（主执行猫 46+47 + QA审查猫），operator拍板。
> operator原则：**越宏观越关注，越细节越放手。**

## operator拍板（宏观层）

必须等operator确认后才能执行：

| 类别 | 示例 |
|------|------|
| 重要架构决策 | 新 ADR、存储方案变更、协议变更 |
| 安全与数据不可逆 | 生产 Redis 操作、删除用户数据、权限模型变更 |
| 成本显著变化 | 引入新付费 API、大幅增加 token 消耗 |
| 对外行为变化 | UX 变化、API 契约变更 |
| 新增外部依赖 | 新 npm 包、第三方服务 |
| 优先级与路线图 | Feat 排序调整、Phase 计划变更 |

## 三猫讨论（中间层）

猫猫之间讨论达成共识，重大分歧升级给operator：

| 类别 | 示例 |
|------|------|
| 设计方向 | 多视角方案选型 |
| 工作流/SOP 变更 | 流程规则调整 |
| 新协作规则 | 猫猫指引文件规则新增 |
| 跨猫职责边界 | 谁负责什么的调整 |

## 猫猫自治（细节层）

猫猫自行判断即可：

| 类别 | 示例 |
|------|------|
| 实现细节 | 算法、数据结构、内部 API |
| 重构择优 | 不改外部行为的代码重组 |
| 测试补齐 | 补测试、提高覆盖率 |
| Bug 修复方案 | 不涉及架构变更的修复 |
| 代码风格 | 命名、格式、注释 |
| 文档跟随更新 | 跟随代码变更的文档同步 |

## 可逆性维度（正交叠加层）

> 来源：2026-05-08"外行领导内行"讨论收敛。
> 核心问题：三层分级管"谁拍板"，但没管"该不该上桌"。大量可回滚决策被升级到 operator，operator 看到的是看不懂的技术 A/B 题。

**规则：回滚成本是独立于类别的正交维度。** 即使一个决策按类别属于"宏观层"，如果回滚成本低**且不碰下列硬排除**，猫猫可自决+事后通报。

**硬排除（无论回滚成本多低，都不能自决）**：愿景/产品方向变更、安全/权限模型变更、生产数据/production data boundary操作、新增外部依赖（npm 包/第三方服务）、显著成本变化（新付费 API）、对外契约变更（API/UX）。这些必须走 operator 拍板或至少 Packet。

```
              可逆（双向门）                不可逆（单向门）
┌──────────────────────────────┬──────────────────────────────┐
│ 高影响  │ 猫猫自决 + 事后通报  │ operator 拍板（必须带 Packet）   │
│         │ （错了一个 commit 改回）│                             │
├──────────────────────────────┼──────────────────────────────┤
│ 低影响  │ 猫猫自决             │ operator 拍板（虽小但回不去）    │
│         │ （连通报都可省）      │                             │
└──────────────────────────────┴──────────────────────────────┘
```

**判断"可逆"的标准**：改回来只需要 ≤1 个 commit + 不影响外部用户/数据/契约 + **不在硬排除列表中**。

**判断"高影响"的标准**：改动影响多模块 / 影响其他猫的工作 / 改变了用户可见行为。

**事后通报格式（一句话）**：`"自决：选了 A，因为回滚成本低（一个 commit），B 的收益不够明显。反对可提。"`

## operator Decision Packet（升级时必带）

> 核心原则：**不给 operator 技术 A/B 选择题，给价值取舍题。**
> 信息不能被压扁——operator 收到的不能只剩"选 A 还是 B"，必须带 trade-off 权重和边界条件。

**任何向 operator 升级的决策（包括 collaborative-thinking 收敛、Design Gate OQ、cross-cat-handoff 给 operator 的 Open Questions）都必须包含 Decision Packet。**

### 格式

```markdown
## Decision Packet

**TL;DR：推荐 X，因为 {一句话价值取舍}。如果你信我们，下面不用看。**

- 为什么需要 operator：愿景级 / 不可逆 / 成本显著 / 跨猫僵局
- 如果选错：回滚成本 低/中/高 + 怎么回滚
- Trade-off 权重：{速度 / 稳定性 / UX / 成本 / 可维护性} 哪个最重要
- 边界条件：在什么前提下推荐成立；前提不成立就选备选
- 反对意见：谁反对 + 是 blocking objection 还是偏好差异
- 真正需要你判断的一句话：我们更愿意牺牲 X 换 Y 吗？
```

### 规则

1. **TL;DR 必须在第一行**——5 秒拍板路径。剩余字段是审计材料，不是阅读材料
2. **如果回滚成本低**（见可逆性维度），不应该出现 Packet——猫猫自决
3. **"真正需要你判断的一句话"必须是价值问题**，不是技术问题。❌ "用 Redis cluster 还是 standalone？" ✅ "我们更看重可靠性还是运维简单？"
4. **缺 Packet 的升级 = 被打回**——operator 有权说"先把 Packet 补上再来"
