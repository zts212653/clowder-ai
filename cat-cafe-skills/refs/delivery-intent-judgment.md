# 把原问题带到交付现场

这份方法来自 F309 普通文件接入和 A2A RFC #1356 的回放：需求已经写清，开发和审查仍可能围着当前实现越走越远。它帮助猫判断做得对不对，不是新增表单、阶段或机器门禁。

## 先判断是否已经理解问题

先理解这句话在当前对话里做什么。“帮我赚一个小目标”可能是在举反例或邀请探索，此时一起理解问题，不急着采访成 AC；若确实委托交付，它又缺少期限、资源、风险边界，并把不可保证的外部结果当成交付。再说明不确定性，澄清会改变方案的条件，形成合理的可控范围；不要擅自改成“做个收益面板”就宣布可验收。探索本身可以得到新理解，也可以暂时没有结论，不自动授权产品实现。

已有清楚的 issue、讨论或接受记录时，沿用它；猫能查证的实现细节自己解决。不为填写模板重新采访，不因每次换猫、换 PR 或换入口就要求用户再确认同一方向。

AC 应表达约定的使用结果和重要边界。确定行为可以由测试证明；体验、取舍和是否解决原问题仍由猫结合实物判断。并非所有目标都适合写成二元 AC，更不能用关键词、正则、字段齐全或模型评分自动裁定用户意图。

## 计划与审查看同一件事

从原 issue / 讨论 / 已接受决定出发，理解这次交付答应完成什么，再看计划、diff 与实际结果。关注的是它们是否还是同一个问题，而非引用是否写齐。

- 计划可以拆工作，不能把已接受的整体操作缩成 API、字段或按钮清单。换内容 owner 不等于放弃已确认的交互关系。
- 审查先形成对本次约定结果的判断，再结合实现、安全、数据与契约风险决定是否放行。方向明显不对时指出偏离处，不用积累更多零碎 findings 证明自己认真。
- 有可运行实物就看实物：前端从真实入口走完整操作，后端跑原 issue 描述的使用场景；只有尚无可运行实物的方案或文档交付，才用状态推演判断。暂时无法运行时如实保留未验证部分，不用推演冒充实物验收。截图与测试各有证明范围；真实浏览器加 fixture 不等于真实持久化，无溢出也不等于好用。
- 修审查意见后回看原问题是否还在。只审过某个修复的批准不能扩大成整项认可；此前完整判断仍适用时复用，只重看实质变化和受影响路径，不因 SHA 变化重做全部验收。
- finding 是否值得阻塞，要看它违反的约定或客观风险、可核验的失败和与本次改动的关系。严重缺陷不能因少填字段自动降级，无关建议也不会因为填上“安全”就变成 blocker。

在现有 PR/thread 的请求与结论中说清判断及依据即可，不规定字段、条数、截图数量或固定发言格式。已有 reviewer 承担本次交付的判断；feature close 的整体愿景守护不能替代它，也不必给每张 PR 再加一只守护猫。若确有新价值取舍，按[交流准备与时机](decision-matrix.md#交流准备与时机)带具体差异找用户；实现明显偏离已接受要求时，猫自行修正。

## 用反例检查自己的判断

- **F309 普通 PNG**：画笔和回复接口都有，旧测试也绿，但默认页仍是说明加底部表单，工具脱离画布。对照已接受的作品优先、分模式、就地评论，这次接入应退回；旧 Task 入口的通过不能移给普通 File 入口。
- **A2A #1354 / #1356**：已约定重建整体生命周期、复用既有 owner、失败回到正确对象。只把 QueuePanel 画顺、补一个兼容分支，或把既有实现的异常写成目标状态，都需要回到原约定重新判断；不能因为局部技术论证完整便扩大放行范围。RFC、后续修订与已接受的产品决定一起读，不把最早措辞冻结成永不能改的规则。
- **“赚一个小目标”**：举例就讨论这个反例；确实委托交付才澄清可控工作与不可保证的结果，不先承诺，也不替用户偷偷换目标。
- **已明确的小修**：原 issue 清楚、改变局部、已有证据覆盖时直接修和定向验证；不抄整份 Feature 的 AC、不重启采访、不加一次全家 review。

这些是供猫反证和取舍的例子，不是可由 presence checker 判断通过的样本答案。判断方法是否省心有效，要看后续真实交付；本次回放不证明总体效用。
