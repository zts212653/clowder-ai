# 星系协作契约

适用于多现场共同交付、动态排班与小团队。星系是帮助理解的比喻：**责任有归属，通讯可横向，角色随任务变化。** 不创建新的权限层、Task 类型或指挥审批层。

## 三种现场，不是三等猫

| 现场 | 对什么负责 | 何时回流 |
|------|------------|----------|
| 主星：指挥与理论 | 维护已接受的愿景、拆交付与依赖、推动阻塞解除、守护验收后的实际结果 | 向用户说明整体实得、差距与真正需决策的取舍 |
| 行星：Phase 执行 | 在授权范围自主实现、选非作者审查、修复、门禁、交付；直接对接其他执行现场 | 完成整项委派一次回流；无法在既有责任路径解决的冲突及时升级 |
| 运行后验收现场 | 核真实加载版本，走原始用户旅程，区分已交代码与实际体验 | 失败带复现和证据回原责任方；整体结论回指挥现场 |

指挥现场的责任组可以有多只猫，但每项待办、共享写入面和等待条件都要有明确当前责任猫；“大家负责”不能使球无人持有，也不把现有单 owner Task 改成多人 owner。

三种现场是职责区分，不强制创建三条 thread。新建遵循 `thread-orchestration` 的独立交付判据与 proposal 流程。小项目可以在同一现场分阶段完成；大项目分开保留上下文。运行后验收的“运行”可以是本地应用、部署服务或其他真实交付载体，不要求外部项目照搬 Clowder AI 的端口与命令。

## 动态角色与小团队

- 分配单位是**本次任务 + thread + 猫身份**，不是固定模型职级。Astra、Opus、Fable 都可以执行；Kimi、GLM 都可以维护指挥与验收职责。这些只是例子，不是必备名册。
- 先核实际成员与任务适配，再考虑可用性、成本和验证手段。不能用价格或单项 benchmark 推定所有任务的能力排序；缺本地 dossier 时从真实履历/工具能力判断，不要求先建立一套档案。
- 两猫家庭示例：Kimi 持整体交付并实现 A，GLM 实现 B；彼此审查对方的改动（当地风险规则允许且能力适配时），指挥责任不使任何一方免审。涉及自己实现的整体验收，保留独立验证和用户验收边界。
- 只有一位当前可用成员时，先做可独立推进的工作。需要独立 review 的改动停在批准前，寻找实际合格非作者或规则允许的人类独立审查；不得用另一 thread、同身份 subagent 或“暂任 reviewer”自批。低风险可免审的情形只消费原有 SOP，团队小不是豁免理由。
- 同一 catId 在不同 thread 不共享上下文、球权或责任记录。角色切换要回读该现场的授权与交付范围；不能把另一现场的资格带过来。

## 通讯找真正的消费者

```text
用户 ↔ 指挥现场：愿景、整体结果、价值取舍
           ↓ 授权范围内的完整工作包       ↑ 整项完成 / 必要升级
       执行 A ←── 接口、依赖、审查、冲突 ──→ 执行 B
           └──── 可验运行版本与旅程 ────→ 验收现场
                         原责任方 ←── 失败证据
```

依赖交付直接给 consumer：确切 source/产物版本、影响、解锁条件；用 `cross-thread-sync` 查真实 thread/cat 并读取发送回执。实施责任交接用 `custody-recognition` / `cross-cat-handoff`；普通 review 用 `request-review` 的直接 carrier 与 typed verdict。通知、协调、FYI 不新增授权，也不转移 owner。

`final-only` 指向**交代的整项工作**，不是每个 commit 或 PR。测试绿、review-ready、小片合入、正常等 CI/依赖都留在执行现场/现有状态源。直接交付 B 所需接口不抄送主星；等待条件与责任记在既有计划/Task/workflow，不再复制一份账本。用户明确要求里程碑报告时才选对应模式。

升级到主星的情形：实际范围/权限/愿景取舍、双方按既有规则仍无法解决的共享写入冲突、依赖失去责任方或超出既定等待边界且无法自行处置。给证据、已尝试路径、影响和自己的建议；普通选 reviewer、已有 owner 在处理的红灯不升级。不可逆与 operator 决策遵守原授权，不通过“指挥批准”绕过。

接收方先核归属，再按真实责任接/退/升。系统送达回执无需礼貌 ACK；有新事实才语义回复。持久化、路由唤醒、正文消费、业务处理、实际播报是不同证据，不能用“工具已返回”替代任意后项。处置依原 carrier 的 typed completion / 等待机制，不用一段总结代替。

## 完成回流与运行后验收

工作包至少说明：主 thread、授权源与当前责任、整项交付条件、单写面、直接依赖方、现在可做什么、在哪个条件前停下、结果回哪。字段放现有计划/任务描述即可；不要求额外表格或每个动作向指挥登记。

回流时说明“交付了什么、证据在哪、运行上还缺什么、剩余责任由谁持有”。有意只委派接口切片时，该切片可独立完成；不能临近汇报才把整个 Phase 缩成刚合入的小 PR。

| 证据层 | 可声称什么 | 不能替代什么 |
|--------|------------|--------------|
| 候选 / 审查通过 | 当前分支在指定验证下成立 | 已合入 |
| main 已合入 / 包已发布 | 确切提交或不可变包已可消费 | 用户实例已升级 |
| 运行版本已核 | 目标进程/安装实例实际加载该版本 | 原始旅程已通过 |
| 真实旅程已通过 | 已测条件下的用户体验成立 | 未测场景、单次样本之外的可靠性或整个 Feature close |

指挥组消费最终证据并守护愿景，不默认重新逐行审查所有子 PR。runtime 重启、麦克风/共享、向外部会议发声、真实 writer 等动作分别查现有授权；没有新增权限不能为了验收擅自打开。验收失败返原责任现场，命中新范围再收敛，不在验收现场偷开第二套实现。

## 对外是一只猫猫球

多个主星与执行团队可由统一的前台伙伴承接：对用户维持所选伙伴的身份、上下文与待决事项，后台仍保留真实作者、来源、工作 owner 和权限。前台只路由结果与决策，不自动成为每项实现的 owner，也不要求所有行星经它中转。

这是协作设计对产品的约束，不宣称当前 F317 已支持所有主动 push、并发消费或播报能力；产品能力以真实运行证据为准。

## 反例与压力检查

| 情境 | 合格动作 |
|------|----------|
| 平时指挥的 Astra/Fable 是这次唯一合适执行者，时间紧 | 可以执行；明确本次范围，独立审查仍交合格非作者 |
| 只有 Kimi/GLM，排班模板却要求其他猫 | 用真实两位成员分担/互审；不生成不存在的句柄、不为凑层级建空 thread |
| 唯一作者另开 thread，想赶在下班前自审合入 | 不把换现场算独立性；做可推进部分，批准缺口如实保留 |
| 六条线陆续 review-ready/小片合入，指挥正忙 | 继续各自闭环；仅把可消费接口直接给依赖方，不逐条唤醒指挥 |
| B 等 A 接口，但 A 的另一块能力还在修 | B 做独立部分，按约定消费已交接口；不等 A 整线，也不拿未合候选解已合依赖 |
| 指挥问某执行现场进度，但约定 final-only | 执行猫核事实后直接应答这次查询；不转成持续主动汇报。指挥回答用户时优先查现有状态，不要求六条线重新报数 |
| main 已绿，旧 runtime 仍在运行 | 只报代码落地；获准加载后核版本，再做真实旅程 |
