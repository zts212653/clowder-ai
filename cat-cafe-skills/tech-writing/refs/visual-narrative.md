# 技术文章的视觉叙事

> 在正文立意与证据边界已经成立后加载。它决定“页面怎样帮助读者理解”，不替 `image-generation` 决定具体生成后端。

## 核心命题

图片不是文章写完后的装修。它和标题、小标题、正文、图注一起构成文章的 UI。

技术文章的图有四种工作：

1. **证明**：把真实输入、输出、diff、日志、数据摆出来。
2. **对照**：让 before / after、失败 / 成功、keep / sunset 自己说话。
3. **解释**：把肉眼看不见的机制压成一个可复述的关系或过程。
4. **调节**：封面、转场、氛围图负责情绪和呼吸，不承担技术 claim。

先选工作，再选图。没有工作的图删掉。

## Figure Contract

动手做图前，为每张图填这六行。填不出来，说明文章还没想清楚，不是绘图工具不够强。

```markdown
### Figure N
- Reader question: 读者此刻会问什么？
- Claim: 这张图只承担哪一句话？
- Source: 真实 artifact / 数据 / 脱敏重建 / 明确示意
- Form: screenshot / input-output / diff / comparison / sequence / relationship / atmosphere
- Five-second takeaway: 五秒后读者能复述什么？
- Caption: 脱离邻近正文仍能成立的一句话
```

一图一问。一张图同时解释三个概念，通常意味着它会变成缩小版 PPT。

## 证据阶梯

| 层级 | 视觉材料 | 能否承担关键 claim | 使用边界 |
|------|----------|--------------------|----------|
| A | 真实截图、diff、日志、数据、原始对话 | 可以 | 脱敏，保留 source ref；不要裁掉改变含义的上下文 |
| B | 基于真实机制的具体案例重建 | 可以辅助 | 图内或图注明确写“示意”；不编造实测数字 |
| C | 流程图、关系图、抽象机制图 | 只能解释 | 必须标清对象与关系；旁边要有 A/B 级锚点 |
| D | 概念艺术、隐喻插画、氛围图 | 不可以 | 用于封面/转场/情绪，不用来证明技术结论 |

关键 claim 优先用 A；拿不到 A 时用诚实的 B。C 帮读者建模型，D 帮页面呼吸。不要拿 D 冒充 A。

## 从读者问题选视觉形态

| 读者问题 | 首选形态 |
|----------|----------|
| “你说它真的发生过？” | 原始截图、commit/diff、日志片段、数据 |
| “哪里错了？” | 输入输出 + 高亮错误位置 |
| “改完到底有什么区别？” | 并排 before / after |
| “先后顺序是什么？” | 时间线、逐步过程、少节点流程 |
| “谁影响谁？” | 带动词箭头的关系图 |
| “哪些该留，哪些该拆？” | 带理由的决策表，不画抽象道路 |
| “我需要先记住整个世界观吗？” | 一张标注完整的总览图 |
| “这一章需要换气吗？” | 氛围图、照片、漫画或留白 |

截图不天然具体，关系图也不天然抽象。判据是：读者能否从图中指出对象、动作、结果。

## 具体在前，概念在后

推荐顺序：

```
具体任务 → 实际输入/输出 → 标出转折或错误 → 命名机制 → 抽象总览
```

读者先看到“发生了什么”，再知道“这叫什么”。如果开头就是“语义惯性、注意力稀释、收敛空间”，图片只会把名词排得更漂亮。

## 一个核心隐喻预算

隐喻的作用是减少认知成本。每多一套映射，读者就要多翻译一次。

- 正文已经用“河床 / 水流”解释模型，就不要让每张图再分别发明闸门、货物、迷宫、轨道。
- 抽象总览通常保留一张，且直接标出真实对象：模型参数、prompt、context、工具结果、输出。
- 后续 claim 回到具体任务：一行 diff、一次错误回答、一份 keep/sunset 表。
- 如果一张图需要一段话解释图例，先问能否换成真实输入输出。

## 页面层的节奏

视觉一致不等于每张图同构。真正的一致来自字体、颜色、留白和语气；信息形态应该随 claim 变化。

- 连续三张同景别、同构图的概念图，会让读者把它们当背景纹理。
- 概念密集处用对照或示例降低认知负担；故事高潮可直接展示原始 artifact。
- 图前一句提出问题，图后一句交付结论。不要正文提前把图说完，再让图重复一次。
- 图注必须独立：不要写“如上图所示”，直接写图证明了什么。
- alt text 描述对象、动作和关系，不写“精美的信息图”。

## 真实性与 provenance

视觉越像截图，越需要诚实说明它是不是截图。

- **真实 artifact**：保留 source ref；脱敏不能改变技术含义。
- **案例重建**：标“示意”或“基于真实机制重建”；不能发明 benchmark、耗时、成功率。
- **生成图**：适合总览、封面、氛围与难以拍摄的场景；不把生成的 UI、终端或图表说成运行证据。
- **外部参考**：可以学习它的节奏、构图和措辞方法；技术数字、因果与模型原理仍需 `source-audit`。

## 产物路由

Figure Contract 决定内容后，再选择工具：

- 已有网页、产品、终端、日志、diff → 截取真实 artifact。
- 完整 raster mock、概念艺术、封面、氛围图 → `image-generation`。
- 精确代码、中文、法律文本、可核对标签或可编辑需求 → 按 `image-generation` 的明确边界选择 HTML/SVG/PPT/hybrid；视觉完成度不能牺牲文字真实性。
- 需要读者亲手验证 claim → `concept-demo-design`，不要把交互硬塞进长图。

## 五秒测试

交付前逐张过五问：

1. **缩略图测试**：缩到文章正文宽度，主关系还看得见吗？
2. **遮正文测试**：藏掉上下两段，只看图与图注，能复述 claim 吗？
3. **换文测试**：这张图放进十篇别的 AI 文章也成立吗？成立就是装饰图。
4. **图例税测试**：必须先学一套符号才能懂吗？能否换成具体对象？
5. **真相测试**：真实、脱敏重建、示意、生成四种身份有没有说清？

## 回归案例：Skill 保质期长文

**RED（commit `628cf6f5a`）**：六张图共享统一的冰原河流美术；每个 claim 又被编码成闸门、货物、路径和检查站。视觉完成度高，关键任务、输入输出和去留理由不可见。人类反馈：“这些图有点抽象了，这也太抽象了。”

**GREEN（commit `06bf3f7be4`）**：只保留一张带完整标签的河流总览；其余换成一行 diff、逐 token 句子、项目命令的错误/正确回答、0→1 / 1→100 具体案例和 Harness 决策表。人类验收：“我满意了。”

**回归判据**：以后给隐喻密集的技术文章配图时，如果准备连续生成多张同世界观概念图，先停下来做 Figure Contract。至少一个关键 claim 必须用 A/B 级证据形态；抽象图不得包办整篇。

**近似反例**：用户明确只要封面或品牌氛围图时，D 级图片就是正确产物；不要强塞终端截图或证据卡。
