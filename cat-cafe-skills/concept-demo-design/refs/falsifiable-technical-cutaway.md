# 可证伪技术剖面：从技术名词到 Claim Bench

这份 reference 处理一种特定任务：观众不仅要听懂一套技术，还要能检查它为什么可信、何时会失败，以及当前证据最多允许说到哪里。

它不是通用 Demo 清单。没有技术可信度判题时，继续用普通 concept story、product experience gate 或 journey validation。

## 一句话

把“点击一个技术名词看说明”改成“亲手改变一个变量，看主张会不会输”。

故事负责获得注意力；实验台负责赢得信任。

## 何时触发

满足下面两项才触发：

1. Demo 的主判断包含一项具体技术主张。
2. 观众需要检查机制、证据边界或失败条件，而不只是理解愿景。

以下情况不触发：

- 只讲品牌愿景、用户价值或未来图景。
- 只比较布局、折叠、导航与视觉方案。
- 只验证端到端用户旅程。
- 只有外部 benchmark 数字，却没有完成 source audit。

## 与 7P × 5E 的分工

7P 负责把内部材料编译成技术叙事：先定位价值和难点，再展开原理、流程、算法、工程与证据。

5E 负责限制我们能说多远：存在、净效果、机制解释、跨情境外推与长期价值。

Claim Bench 负责把其中最关键的一项主张变成可操纵画面。它不复制 7P × 5E，也不把七个透镜和五类证据都做成七乘五页面。

## Claim Bench 最小结构

| 字段 | 必须回答的问题 |
|---|---|
| falsifiable claim | 哪个具体句子可能被证伪？什么观察会让它输？ |
| failure mode | 这套机制最可能怎样失效？ |
| competing explanation | 同一现象还可能由什么造成？ |
| technical object | 真正被改变的是哪个状态、数据流、模型、规则或控制面？ |
| algorithm flow | 输入怎样经过关键步骤形成输出？ |
| manipulable variable | 观众能亲手改变哪个变量？ |
| control | 哪些条件保持不变？ |
| ablation | 拿掉声称有效的机制后会怎样？ |
| verdict rule | 哪组可观察状态映射到 SUPPORTED、REFUTED 或 UNKNOWN？ |
| claim ceiling | 当前结果明确不能推出什么？ |
| provenance | 数字、样本、规则和案例分别来自哪里？ |

## 从 failure mode 反推实验

不要先列组件再给每个组件做按钮。先问主张最可能在哪里被误判。

例：主张“轨迹归因能找出真正造成失败的步骤”。

1. competing explanation：失败可能只是任务更难，不是某一步变差。
2. control：固定任务、模型、工具版本和判分规则。
3. manipulable variable：只替换一个候选步骤的输出。
4. ablation：移除归因模块，改用最近一步或最高 token 步骤作为解释。
5. verdict：只有替换被归因步骤能稳定改变结果，而替换无关步骤不能，才显示 SUPPORTED。
6. claim ceiling：这只能支持该 fixture 上的局部贡献判断，不能宣称识别了现实任务中的唯一因果。

这个顺序很重要。交互是失效机制的测量仪，不是页面装饰。

## 画面组成

每个 bench 保留五个可见区域：

1. **主张卡**：一句可输的 claim 与 claim ceiling。
2. **机制剖面**：技术对象和 algorithm flow，只画影响判题的步骤。
3. **操纵台**：一个主变量、一个 control 和一个 ablation。
4. **观察窗**：展示变量变化后真正改变的中间状态与结果。
5. **verdict 条**：由确定规则给出 SUPPORTED、REFUTED 或 UNKNOWN，并解释哪条条件命中。

多个 claim 可以共用页面壳和状态机，但不要共用一个含混 verdict。一次交互只判一件事。

## 三类证据不要混

### 确定契约

按钮能否改变声明变量、control 是否冻结、verdict 映射是否正确，交给 test、guard 和浏览器重放。

### 外部事实

论文数字、benchmark、趋势和因果对比先走 source-audit。Claim Bench 只消费带 provenance 与适用边界的事实。

### 不确定效用

只有明确 consumer 会据此 keep、tune 或 sunset 某项能力时，才走 eval-design。单次讲解页不因“有实验”就自动出生为长期 Eval。

## 诚实状态

建议每项 claim 使用四态：

- **理论谱系**：有相关思想或论文，不等于家里已实现。
- **家内已实现**：有代码、PR 或可重放行为证据。
- **效果已验证**：有匹配对象、基线和证据窗口。
- **尚未闭合**：机制存在，但效用、归因或外推仍未知。

预期结果、设计愿望和自评不能改名成 outcome 回灌。假设可以展示，但必须继续叫 hypothesis。

## Pressure Test

### Standard

请求：“把归因讲清楚，让我试试它会不会把最后一步错当根因。”

通过：一个归因 claim，一个任务难度 control，一个候选步骤操纵，一个 naive baseline ablation，一个确定 verdict，一个局部 claim ceiling。

### Boundary

请求：“给发布会做一支有感染力的未来故事。”

通过：不强塞 Claim Bench；只在出现具体技术可信度 claim 时启用。

### Conflict

请求：“引用论文的 30% 成本下降，做个按钮证明我们也能降 30%。”

通过：先 source-audit；若对象、基线和实现不匹配，页面只能标理论谱系或待验证，不把外部结果改写成自家效果。

## 常见失败

- **名词按钮**：点击“归因”只换一段解释。修正：让观众改变候选原因并看到 verdict 翻转。
- **永胜实验**：无论怎么操作都显示技术有效。修正：先定义 REFUTED 条件。
- **多变量同动**：模型、prompt、工具和样本一起变化。修正：一次只操纵一个变量。
- **旁白裁决**：页面没有规则，讲者说“所以成功”。修正：把 verdict 映射写进状态机和测试。
- **概念冒充效果**：模拟数据推出生产收益。修正：显式 claim ceiling 与 truth label。
- **理论贴纸**：堆论文名但看不到机制。修正：只保留能解释 failure mode 或 algorithm flow 的理论锚点。

完成标志不是页面看起来很科学，而是陌生观众能回答三句话：

1. 它声称解决什么？
2. 我怎样让这个主张失败？
3. 这个实验尚且不能证明什么？
